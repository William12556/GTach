## 1. Summary

`prompt-2b6f4d91-palette-long-press-toggle.md` was implemented in full. Three
edits across the two permitted files, one commit, `98a1168`.

A long press on the RADIAL gauge now reaches `_toggle_palette`. The route is
a direct call from `TouchHandler._handle_long_press` to
`DisplayManager._handle_long_press` — the same route `change-3e8b1d72` used
for the vertical swipes, and the only route that runs. The inert double-tap
registration is gone, so exactly one invocation path exists.

Twenty-one checks were written. They were run against the **pre-change** files
first and returned **6 of 21 passing**, with the acceptance check failing on
the recorded evidence — no delegation, and a `Long press: no action` DEBUG line
in the captured log. Against the post-change files they return **21 of 21**.
The suite discriminates; a test that had passed both ways would have proved
nothing, which is the trap the prompt named.

`pytest tests/` is 11 passed, unchanged from before the edit.

**Not verified on target.** Everything below is bench evidence. Whether a
one-second press is comfortable on the panel, whether the operator's muscle
memory sends them looking for OPTIONS, and whether the night palette is legible
at night are the operator's trial and are not answerable here.

## 2. What Was Changed

One commit, `98a1168`, two files, +31 / −27 lines.

### 2.1 `src/gtach/display/manager.py` — edit 1, the rename

`_handle_double_tap` is now `_handle_long_press`. **The body is byte-identical**:
the setup-mode guard, the RADIAL guard, the `_toggle_palette()` call, the
`SETTINGS_CHANGE` return and the exception handler returning `NONE` are all
untouched.

The docstring is the prompt's text verbatim, including the paragraph stating
that this is *not* the OPTIONS toggle a method of the same name performed until
`change-3e8b1d72` deleted it. That paragraph is the point of the edit: the git
history now shows `_handle_long_press` leaving `DisplayManager` in one commit
and returning in another, meaning something entirely different.

### 2.2 `src/gtach/display/manager.py` — edit 2, the inert registration

The conditional block —

```python
_double_tap = getattr(GestureType, 'DOUBLE_TAP', None)
if _double_tap is not None: ...
else: self.logger.debug('GestureType has no DOUBLE_TAP; ...')
```

— and its preceding comment are deleted, replaced by the prompt's comment
recording that coordinator gesture callbacks are never dispatched and that the
palette toggle is therefore wired from `touch.py`.

The `SWIPE_DOWN` and `SWIPE_UP` registration calls above it are **byte-identical**,
verified by diff. They do nothing. Removing them is out of scope precisely
because the operator has confirmed the swipes working, and the cost of being
wrong about *why* they work is a broken instrument.

`GestureType` remains imported and remains used by those two calls, so no
import change was needed.

### 2.3 `src/gtach/display/touch.py` — edit 3, the delivery

`self.logger.debug('Long press: no action')` is replaced by

```python
self.display_manager._handle_long_press((x, y), (x, y))
```

with the prompt's comment above it explaining the direct call and the doubled
position. The `DISCONNECTED` early return above is untouched and still returns
before this line is reached. The surrounding `try`/`except` is unchanged. The
pre-existing comment about OPTIONS being reached by swiping was retained rather
than replaced — it explains why the method has no mode change of its own, which
is still true.

## 5. Findings and Deviations

**No deviations.** All three edits are the prompt's specified text.

Two stale references were left in place because correcting them would have
meant departing from text the prompt specified verbatim or from a body it said
does not change. Both are cosmetic, neither affects behaviour, and both are
recorded here for the operator to decide on:

### 5.1 `Double tap handling error` in the renamed handler

The handler's exception branch still reads:

```python
self.logger.error(f'Double tap handling error: {e}')
```

The prompt states twice that the body does not change, and enumerates the
exception handler among the things that stay. It was left. The consequence is
that if `_toggle_palette` ever raises past its own handler, the log will name a
gesture that no longer exists. A one-word edit — `Long press handling error` —
would fix it, and would be worth folding into the next change that touches this
method.

Note that `grep -n DOUBLE_TAP` is unaffected: the string is `Double tap`, not
the member name, so the success criterion holds as written.

### 5.2 `touch.py:202-209` in the manager.py comment

The prompt's comment text cites the swipe delegation at `touch.py:202-209`.
That was correct when the prompt was written. Edit 3 adds eight lines above it,
so the swipe delegation now sits at `touch.py:210-218`. The comment was written
as specified and is therefore off by eight lines from the moment it landed.

The reference is to a well-named pair of calls in a short method, so it is
findable regardless. Recorded rather than silently corrected, because the
prompt gave the text to insert.

### 5.3 An observation on the wider defect, reported not acted on

The prompt asked that the wider repair be reported rather than done if it
seemed necessary. It is not necessary for this change — the direct call works
and is proven — but the analysis in `issue-2b6f4d91` was independently
confirmed while implementing:

- `handle_touch_up` and `handle_touch_move` have no callers in `src/gtach`
  outside their own definitions and the abstract declarations in
  `interfaces.py`.
- Therefore every `register_gesture_callback` registration is inert, and the
  two surviving ones in `manager.py` are decorative.

The cost of that is not the palette toggle, which is now fixed, but the next
feature wired the same way. `register_gesture_callback` logs
`Registered callback for SWIPE_DOWN` on success, and that line is in every log
pulled to date, for a callback that has never been invoked. A registration
mechanism that reports success and never fires will mislead again. The comment
added by edit 2 is the only in-tree warning; whether that is enough is a
judgement for the operator, and the repair itself remains recorded in
`change-2b6f4d91`'s `alternatives_considered` as the correct long-term fix.

### 7.1 What the operator needs to check on `gtach.local`

The bench cannot answer any of these:

1. A long press on the gauge changes the palette, and `debug.log` gains a
   `Palette switched to night` line — a line that appears in no log to date.
2. The transient `Night` / `Day` confirmation renders and clears.
3. A second long press returns to day.
4. The choice survives a restart.
5. Swipe down and swipe up still enter and leave OPTIONS.
6. The options-screen buttons still respond.
7. A long press held over an options button does nothing to the palette.
8. **At night: whether the night palette is legible.** This is the half of the
   §6.1 contrast question that has never been answerable, because the panel has
   never shown the palette. Day blue measures 2.21:1 and night blue 1.55:1
   against a 3:1 criterion; the day face has been seen and reads well, which
   already suggests the criterion is the wrong test for a deliberately dark
   face. The night face is the remaining evidence.

Expect confusion on point 1. Long press did nothing in the build the operator
is running and opened OPTIONS in the build before that. The on-screen
confirmation is what makes an accidental toggle explain itself.
