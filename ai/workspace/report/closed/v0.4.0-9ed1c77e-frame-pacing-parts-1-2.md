## 2. What Was Changed

### 2.1 Part 1(a) — `import queue` hoisted to module scope

`import queue` sat inside `_draw_radial_mode`, on the non-simulation branch that
drains the OBD message queue — so it executed on every RADIAL frame, 60 times a
second. It now sits with the stdlib imports at `manager.py:20`, between
`logging` and `threading`.

The only consumer, `except queue.Empty:` at `manager.py:886`, is unchanged and
still resolves. The `import` line was the sole deletion; the comment above it
("Drain queue — keep only the latest value to avoid display lag") was left in
place.

### 2.2 Part 1(b) — the radial debug f-string guarded

`manager.py:1127` was:

```python
self.logger.debug(f'Radial mode: RPM={rpm:.0f}')
```

The f-string is formatted by the interpreter *before* the call, so its cost was
paid at the frame rate whether or not DEBUG was enabled — and production
configures a `NullHandler`, which discards the record after the formatting has
already happened. It is now:

```python
# The f-string is formatted before the call, so at 60 Hz
# the cost was paid whether or not DEBUG was enabled —
# and production configures a NullHandler
# (display review §5.6, recommendation 14).
if self.logger.isEnabledFor(logging.DEBUG):
    self.logger.debug(f'Radial mode: RPM={rpm:.0f}')
```

The comment is the prompt's text verbatim. `logging` was already imported at
module scope (`manager.py:19`), as the prompt anticipated; nothing was added for
it.

This is the only site guarded. Other per-frame `logger.debug` calls exist in the
file (for example the queue-drain error handler two lines below the hoisted
import) but the prompt named one site and only that site was touched.

### 2.3 Part 2 — `fps_limit` 60 → 30

`config/config.yaml:29`, under `display:`. One line, one value. Nothing else in
the file was touched — the diff is `-  fps_limit: 60` / `+  fps_limit: 30` and
nothing more.

The file still parses; the surrounding keys (`mode`, `rpm_warning`, `rpm_danger`,
`touch_long_press`, the `splash` and `rpm_bands` blocks) are byte-identical.

## 6. Findings

No deviations from the prompt's Part 1 and Part 2 text. Three findings.

### 6.1 Part 2 changes only the deployed config, not the defaults

`config/config.yaml` is the sole file the prompt permits, and it now reads 30.
But `fps_limit` defaults to **60** in six other places:

- `src/gtach/utils/config.py:555` — the `DisplayConfig` dataclass default
- `src/gtach/utils/config.py:583` — `data.get("fps_limit", 60)`
- `src/gtach/utils/config.py:1347` — the INI reader's fallback
- `src/gtach/display/models.py:173` — the display-side dataclass default
- `src/gtach/display/manager.py:445` — `config_data.get('fps_limit', 60)`
- `src/gtach/utils/default-config.txt:24` — the shipped default config

A runtime that reads the deployed `config.yaml` gets 30. A runtime that falls
back to defaults — a fresh install before the config is written, or any path
where the display section is missing — still gets 60. None of these were
touched, correctly: the prompt's constraint is explicit that only two files may
change. Flagged so that the on-target result is read against the right value,
and so a future cycle can decide whether the defaults should follow.

`src/gtach/utils/config.py:398` already recommends "reducing FPS limit from
{fps_limit} to 30 or lower for better Pi performance" when the value exceeds 30.
That recommendation will now stop firing for the deployed config — a small,
correct side effect.

### 6.2 Part 2 slows the shift-cue flash by 6.7 percent

`_get_shift_cue` derives the flash from the frame counter, not from wall-clock
time: `half_period = max(1, int(round(self.config.fps_limit / 4.0)))`. At 60 that
is 15 frames = 0.250 s; at 30 it is 8 frames = 0.267 s, because `round(7.5)` is 8
under banker's rounding rather than 7.5 frames.

So the cue's half-period lengthens by 17 ms and the full cycle by 33 ms — 1.88 Hz
where it was 2.00 Hz. Harmless and almost certainly imperceptible, but it is a
real behavioural consequence of a change documented as "one value", and worth
having on record before the on-target check. Both values are asserted in §4.2.

The startup spinner (`manager.py:1607`, `step = max(1, int(round(fps_limit /
8.0)))`) is unaffected: `round(60/8) = 8` at 60 Hz and `round(30/8) = 4` at 30 Hz,
both 0.133 s per step.

### 6.3 The prompt's line references have drifted

Recorded at §3 for the Part 3 session. Every line number in the prompt is roughly
80-140 lines short of the current file, which suggests the prompt was written
against the file before change-4c038bed and change-5012004e landed. The two Part 1
sites were located by content, not by line, and the correct current lines are
given in §2.
