## 1. Summary

`prompt-3e8b1d72-options-swipe-navigation.md` was implemented in full. Six
edits across the two permitted files, one commit, `a8dcbea`.

A downward swipe now enters OPTIONS and an upward swipe returns to the screen
it was entered from, in **both** live handler paths. The long-press toggle is
retired from both. The mode in use on entry is recorded and restored, so an
exit from the disconnected screen returns to the disconnected screen and not
to a dataless gauge.

Twenty-six checks were written and all pass. More usefully, the suite was run
against two deliberately broken variants — the two failure modes the prompt
names as "ways to get this wrong, both of which compile" — and it caught both,
by the exact checks that should have caught them.

**Not yet verified on target.** Everything below is bench evidence. Whether a
vertical swipe is comfortable on a round bezel-less panel, and whether it fires
by accident while driving, is the operator's trial and is not answerable here.
The recorded fallback — re-registering LONG_PRESS alongside the swipes — is one
line and remains available.

## 3. What Was Changed

One commit, `a8dcbea`, two files, +124 / -36 lines.

### 3.1 `src/gtach/display/manager.py`

| Edit | Location | Action |
|---|---|---|
| 1 | `__init__`, beside `_options_view` | `self._pre_options_mode = None` added, with the comment recording why the exit is not simply RADIAL. |
| 2 | Beside `_handle_double_tap` | `_handle_swipe_down` and `_handle_swipe_up` added. |
| 3 | `_setup_touch_callbacks` | The `LONG_PRESS` registration replaced by `SWIPE_DOWN` and `SWIPE_UP`. |
| 4 | — | `DisplayManager._handle_long_press` removed entirely; `_draw_options_menu`'s footer changed to `"Swipe up to return"`. |

Both handlers follow the existing gesture-handler convention exactly: guard,
act, return a `TouchAction`, and catch-log-return-`NONE` on failure. Each
rejection path logs at DEBUG with the reason, so an unresponsive swipe is
diagnosable from the log — the prompt's stated logging requirement.

`_handle_swipe_down` returns `NONE` in setup mode and in OPTIONS, SPLASH or
ACKNOWLEDGEMENT; otherwise it records `_pre_options_mode`, resets
`_options_view` to `'menu'`, sets the mode to OPTIONS and returns `NAVIGATION`.
`_handle_swipe_up` returns `NONE` in setup mode and unless the mode is OPTIONS;
otherwise it resets the sub-view, restores `_pre_options_mode or RADIAL`,
clears the record and returns `NAVIGATION`.

The conditional DOUBLE_TAP block of `change-5012004e` sits immediately below
the registration that was replaced and **does not appear in the diff at all** —
it is byte-identical.

### 3.2 `src/gtach/display/touch.py`

| Edit | Location | Action |
|---|---|---|
| 5 | `_handle_short_press` | Vertical-swipe detection inserted **between** the setup early return and the OPTIONS early return, delegating to the DisplayManager handlers. |
| 6 | `_handle_long_press` | The mode-changing branch replaced by a DEBUG log. The disconnected early return above it is unchanged. |

**The ordering is the point of EDIT 5.** The swipe test sits after the setup
early return and before the OPTIONS early return. Placed after the OPTIONS
return — which compiles and passes a careless reading — every short press
inside OPTIONS would route to `_handle_options_touch`, the upward exit would
be unreachable from the legacy path, and the coordinator path would be the only
way out. That is the single-route failure this change exists to remove,
reproduced in a new form. §4.3 records the mutant that proves the ordering is
tested rather than merely asserted.

The legacy path **delegates**; it does not reimplement the entry and exit
rules. That is what makes the two paths agree by construction rather than by
discipline, and it is why the principal test passes rather than merely
happening to agree today.

## 4. Testing

### 4.1 Method

The suite drives a **real `TouchEventCoordinator`**, so registration and
dispatch are exercised rather than mocked: `handle_touch_down` then
`handle_touch_move` with a 150 px vertical movement, which the coordinator's
own `_recognize_gesture` classifies as SWIPE_DOWN or SWIPE_UP and dispatches to
whatever `_setup_touch_callbacks` registered. The registration under test is
performed by calling the real `_setup_touch_callbacks`, not by hand.

`pygame`, `yaml` and `psutil` are stubbed and the two `__init__.py` files that
import them are bypassed; `DisplayManager` is built with `__new__` and given
only the state the gesture handlers read, since its constructor needs a display.
The harness lives at `<scratchpad>/test_swipe_navigation.py` and is not
committed — it is a bench instrument and the prompt prohibited creating files.

## 6. Findings and Deviations

### 6.1 `pytest tests/` remains a criterion that cannot fail

pytest is not installed on this machine and `tests/` collects zero items where
it is. Recorded as vacuous rather than as a pass, as in the `7f2a9c04` report.
The 26-check harness carries the evidence instead. This is a standing property
of the repository, not a consequence of this change.

### 6.2 A second footer still says "Long press to return", and it is now wrong

`_draw_update_view` draws `"Long press to return"` at `manager.py:1672`. The
prompt scoped the footer edit to `_draw_options_menu` and the success criteria
name only that one, so it was left alone.

It is now a false instruction. The update sub-view is reached from OPTIONS with
`config.mode` still OPTIONS, so a long press there does nothing at all, while an
upward swipe exits OPTIONS entirely. The correct text is arguably not the same
string as the options menu's — from the update view an upward swipe leaves the
options screen rather than returning to the menu, so `"Swipe up to return"` is
true but slightly understates what happens.

**Recommend a follow-on triple.** It is a one-string edit in a file this change
already touches, but it is a visible-text change outside the specified scope and
outside the criteria, and inventing it here is precisely the class of decision
that `prompt-378703da`'s scope mismatch shows should be made in the document
rather than by the executor.

### 6.3 The legacy path reads the coordinator's threshold — 50 px, not 100

The prompt specified `abs(dy) >= 100` and added: "If the coordinator's
`swipe_threshold` is readable from here, prefer it and say so in the commit
message." It is readable — `self.display_manager.touch_coordinator.swipe_threshold`
— and its value is **50**, not 100. The implementation reads it through a
`getattr` chain that falls back to 100 if the coordinator is unavailable, which
it can be: `touch_coordinator` is assigned inside `_initialize_components`'s
`try` block, so a failed rendering-engine initialisation could leave the
attribute unset.

The consequence, stated plainly: **the legacy path now accepts a 50 px vertical
movement as a swipe where the prompt's literal text would have required 100.**
That is the preferred option the prompt asked for, and it is what makes the two
paths accept the same movement — but it is half the literal figure, and a 50 px
movement is easier to make by accident. If the on-target trial shows accidental
entry, this is the first number to look at, and raising the coordinator's
`swipe_threshold` now moves both paths together. It is recorded in the commit
message as required.

### 6.4 The gesture fires mid-drag, and the following touch-up is unguarded

The coordinator dispatches a recognised gesture from `handle_touch_move`, not
from `handle_touch_up` (`touch_coordinator.py:265-271`). OPTIONS therefore
appears while the finger is still down, and the subsequent touch-up lands on the
newly shown screen. The prompt flagged this as an edge case to confirm rather
than to fix.

Bench evidence is partial: `handle_touch_up` after the gesture returns without
a button press in the harness, because the OPTIONS regions are registered by
`_register_view_regions` during a render pass that a headless harness does not
run. On target the regions will exist. Whether a downward swipe that ends over
the Clear-settings button activates it on release **is not answered by these
tests** and should be watched for during the trial: swipe down so the finger
finishes low on the screen, and confirm nothing is pressed.

This is a pre-existing property of the coordinator's dispatch timing, not
something this change introduces, and `display/input` was out of scope.

### 6.5 Two long-press behaviours survive deliberately

`TouchHandler._handle_long_press` keeps its disconnected early return, which
logs the intent to enter SETUP. A long press while disconnected still does that
and nothing else — asserted.

The coordinator's default handling still returns `TouchAction.NAVIGATION` for
an unregistered LONG_PRESS (`touch_coordinator.py:355`). Nothing consumes it and
no mode changes, which is asserted, but the gesture is not inert at the
coordinator level. Left alone: `display/input` was out of scope, and the same
paragraph of the change document records the equivalent `MODE_CHANGE` default
for the horizontal swipes as knowingly left in place.

### 6.6 `_pre_options_mode` survives a swipe-less exit as a stale record

Nothing else in the codebase clears `_pre_options_mode`. If OPTIONS is left by
some route other than `_handle_swipe_up` — none exists today — the recorded mode
would persist and be applied by the next upward swipe. The default path is
correct because entry always overwrites the record before an exit can read it.
Noted as a property to preserve rather than a defect: any future exit route must
clear it, or it must be cleared on entry to a non-OPTIONS mode instead.
