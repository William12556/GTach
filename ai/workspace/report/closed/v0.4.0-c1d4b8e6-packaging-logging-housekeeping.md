### 2.1 Retrieval form used

**`sys.modules.get('gtach.main')`**, not `importlib.import_module`. The prompt
accepts either and asks which was used. `sys.modules.get` was chosen because it
is a plain dict lookup with no import machinery behind it, and because its
`None` return composes directly with the `if _main is None: return` guard the
prompt specifies — matching the existing guard style in both methods.

`import sys` was already present in both methods (`app.py:137` and `:154`); no
import was added or moved.

Nothing else inside either method changed. The platform guards, the handler
`None` checks, the `setLevel` calls, the log lines and the surrounding
`try/except` are byte-identical to their previous text. The comment above each
retrieval records why the obvious form does not work, so the next reader does
not re-derive it.

### 2.2 Repository-wide grep

The prompt required grepping for the pattern rather than trusting the two named
sites. `grep -rn "from . import main"` over the whole tree found exactly the two
sites, both in `app.py`. No third site exists.

A related but distinct form, `from .main import main`, appears at
`src/gtach/__init__.py:11` (the cause, deliberately untouched),
`src/gtach/__main__.py:11` and `bin/build.sh:81`. None is the faulty pattern:
each imports the function deliberately and by name, which is exactly what it
gets.

## 5. Findings and Deviations

No deviations from the prompt. Four findings.

### 5.1 The test trap — the fault reproduces itself inside the harness

The first version of the discriminating test **passed 9/9 against the
pre-change code**. It was written the obvious way:

```python
import gtach.main as gmain
gmain._debug_handler = h
```

`import a.b as c` resolves `c` by `getattr(a, 'b')` before falling back to
`sys.modules`. `gtach.__init__` has already rebound the package attribute
`main` to the function, so `gmain` was the **function** — and setting
`_debug_handler` on it stored the handler on the very object `app.py` was
wrongly reaching for. The broken code then found the handler and set its level,
and the test reported success.

This is the same shadowing the prompt warns about at `edge_cases`, met from the
test's side rather than the fix's, and it is more dangerous there: a wrong fix
would have been certified by it. The corrected harness takes
`sys.modules['gtach.main']` and asserts `isinstance(gmain, types.ModuleType)`
before proceeding, so the contamination cannot recur silently.

The change document's instruction to write the discriminating test first and
confirm it fails is what caught this. Had the test been written after the fix,
it would have passed and nothing would have been learned.

### 5.2 The grep criterion is unsatisfiable as literally written

Criterion 4 asks that `from . import main` appear nowhere in the repository. It
cannot be satisfied literally: the string appears twenty-four times in the T-Docs
themselves — in `ai/task.md`, in the issue, change and prompt documents for this
very cycle, and in the closed `prompt-bd8f95b7`, which is where the two faulty
sites were originally written.

It also appears twice more in `src/gtach/app.py`, inside the explanatory
comments the prompt's own EDIT A text specifies verbatim.

Read as intended — no executable occurrence — the criterion is met. The prose and
comment occurrences are documentation of the fault and were not removed. This is
the same class of over-literal criterion recorded against `prompt-378703da` in
change-7f2a9c04, and worth the same treatment next time the pattern is used.

### 5.3 `src/gtach/__init__.py` carries a pre-existing modification

It shows as modified in `git status`, but not by this change. The working tree
already carried an uncommitted version bump — `__version__ = '0.2.67'` →
`'0.3.3'` — before this session began, alongside similar pre-existing edits to
`ai/task.md`, `bin/build.sh`, `pyproject.toml` and `src/gtach.egg-info/PKG-INFO`.

The file is byte-identical to its state at the start of this task, which is what
criterion 14 means. Its one changed line is the version string, not the
`from .main import main` re-export, which stands untouched as the change document
requires. `src/gtach/main.py` is byte-identical to HEAD.

**One uncommitted line was swept in.** `pyproject.toml` also carried the
matching pre-existing version bump — `version = "0.2.67"` → `"0.3.3"` — and
because the file had to be staged whole for EDIT B, that line is now in commit
`d6d8992` too. The commit's `pyproject.toml` diff is +12 / −2: eleven lines and
one deletion are EDIT B's `package-data` block, and one line each side is the
version bump. It is flagged rather than reverted — it was the operator's edit,
it is consistent with `src/gtach/__init__.py` and the wheel that was built at
07:58, and undoing it would have desynchronised the two version strings. If a
separate version-bump commit was intended, this line will need lifting out of
`d6d8992`.

### 5.4 Build artefacts were reverted, not committed

Building the wheel regenerated two tracked build artefacts. `src/gtach.egg-info/
SOURCES.txt` gained one line — `src/gtach/assets/engine_profiles.yaml`,
correctly reflecting EDIT B — and a `build/` directory appeared at the root.

`SOURCES.txt` was reverted with `git checkout` and `build/` deleted, so that the
commit contains only the three named files as criterion 16 requires. Both are
generated and will regenerate at the next real build. `src/gtach.egg-info/
PKG-INFO` remains modified, as it was before this session started; it was not
touched.
