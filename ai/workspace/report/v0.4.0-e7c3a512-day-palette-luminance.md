## 4. The Rendered Frame, Call by Call

The prompt's last test scenario asks that a rendered frame use the new colours
and that no other drawing call differ. Rather than eyeball this, the harness
renders one frame per band through the headless arrangement **twice** — once
with the shipped palette and once with the pre-change palette, against the
*same* manager code — and diffs every recorded `polygon`, `line` and `circle`
call including full geometry.

Every frame is **23 draw calls** in both runs, in the same order:

| Band (rpm) | Calls differing | What |
|---|---|---|
| 0 (500) | 2 of 23 | two threshold marks |
| 1 (2000) | 2 of 23 | two threshold marks |
| 2 (4000) | **3 of 23** | two marks + **the fill arc** |
| 3 (5000) | **3 of 23** | two marks + **the fill arc** |
| 4 (5700) | 2 of 23 | two threshold marks |
| 5 (6500) | 2 of 23 | two threshold marks |

Every single difference is colour-only — same call kind, same geometry — and
every one is exactly one of the two intended substitutions. No draw call in any
frame retains an old colour. The fill arc in bands 2 and 3 is the new value.

The two threshold marks differ in *every* frame regardless of active band,
because the boundary-mark list at `manager.py:1301-1306` reads the same tuple;
the prompt names this as intended, being the same information at the rim.

## 5. The One Commit Could Not Be Made

The prompt asks for one commit. I did not make one, and this is the single
respect in which the deliverable is incomplete.

`src/gtach/display/models.py` currently carries **two** uncommitted changes:
`change-64d8d8fc` (the `band_centres` / `band_centres_lit` tuples and the
removal of the three scalar `shift_centre_*` fields, from the previous session)
and `change-e7c3a512` (this one). `manager.py` carries the other half of
`64d8d8fc`. `HEAD` is `2002f82`, which committed docs only.

That leaves two possible commits, and both are wrong:

**Commit `models.py` alone** — which is what "modify only `models.py`, one
commit" would literally produce — pairs the new `Palette` with `HEAD`'s
`manager.py`, which still references the three removed fields at lines 1106,
1113, 1117 and 1122. Not a theoretical concern; I built that exact pairing in a
worktree and ran it:

```
RAISED: AttributeError 'Palette' object has no attribute 'shift_centre_normal'
logged: Shift cue calculation error: 'Palette' object has no attribute 'shift_centre_lit'
```

`_get_shift_cue` raises in the `try`, and its `except` handler **raises again**
on `shift_centre_normal`, so the exception escapes to `_draw_radial_mode`'s
handler. Every RADIAL frame would fail.

**Commit both files** bundles `change-64d8d8fc` — whose issue and change T-Docs
are explicitly still ACTIVE pending your T06 result on `gtach.local` — into a
commit whose stated subject is a two-value palette tweak. That misrepresents the
record and makes `64d8d8fc` awkward to revert if the uniform sweep does not
survive observation.

**The two ways forward**, both yours to choose:

1. **Two commits, in order** — `64d8d8fc` (`models.py` + `manager.py`) first,
   then `e7c3a512` (`models.py`) on top. Clean history, each change revertable
   on its own. This needs the `models.py` hunk split, which `git add -p` does
   in one step since the two edits are 60 lines apart and non-adjacent.
2. **One combined commit** naming both changes, if you would rather not split
   and are content to treat the two as a single display-palette revision.

I have not staged anything. The working tree holds both changes and both are
independently verified.

## 8. Findings and Observations

### 8.1 A harness artefact I corrected

My first identity check compared `NIGHT_PALETTE == PRE.NIGHT_PALETTE` and
failed. `Palette` is a frozen dataclass, and dataclass `__eq__` returns
`NotImplemented` unless `other.__class__ is self.__class__`; the pre-change file
is loaded as its own module, so its `Palette` is a different class object with
identical fields. The palettes were never different. Now compared by value via
`dataclasses.astuple`, with the field-by-field checks retained alongside.

### 8.2 Brightness still does not track urgency, and should not

Worth stating plainly so the change is not later read as half-finished. The
brightness rank, brightest first, is now **3, 4, 2, 5, 0, 1** — caution is the
brightest band on the panel at 0.4562, and danger sits at 0.2126, a factor of
2.15 dimmer.

That is the design, not a shortfall. The prompt's specific requirement was that
torque no longer outrank warning, and that is met. Making the ramp monotonic
would mean brightening danger, and pure red is 0.2126 by definition — leading
the ordering would require diluting it toward pink, discarding the redline
convention for a property the shift-cue flash already supplies. I resisted this,
as the prompt asked, and record the resulting non-monotonicity so it is a known
and accepted property.

### 8.3 This change lands harder than it would have a week ago

`change-64d8d8fc` made the sweep a single uniform arc in `bands[active_band]`
rather than six graduated segments. So where the old graduated arc showed
full-saturation yellow only in the segment above `caution_start`, the uniform
sweep at 5000 rpm paints the **entire** arc from 0 in that one colour — a much
larger area of the panel's brightest element. The 2.03× and 2.49× luminance
reductions therefore apply across the whole sweep, not one segment of it.

The two changes compound in the operator's favour, and it is worth knowing that
the glare being corrected here was itself made more prominent by the previous
change. Neither was measured on target.

### 8.4 Band 3's sweep and centre disc now differ slightly in hue

`bands[3]` is `(205, 180, 0)` with a 12.20% red/green imbalance, Lab hue
**94.25°**. `band_centres[3]` `(89, 89, 0)` and `band_centres_lit[3]`
`(115, 115, 0)` are both pure yellow, `r == g`, Lab hue **102.85°**. An 8.6°
divergence between the caution sweep at the rim and the caution disc at the
centre.

Explicitly out of scope — the prompt forbids touching the centre tuples, and
those were authored against the old full-saturation `bands` in
`change-64d8d8fc`. Almost certainly imperceptible at this saturation. Recorded
because it is the kind of drift that accumulates silently across values changes,
and because if the centre tuples are ever revisited, matching the new hue is a
free improvement.

### 8.5 The comment carries figures that must be maintained with the values

The comment now states four numbers — two luminances and two contrast ratios.
All four are correct as shipped, and the harness re-derives all four rather than
trusting them. If either tuple entry is ever adjusted, the comment must move
with it, or the file will document values it no longer holds. The prompt's
fallback pair at §10 would change all four.
