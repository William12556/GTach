## 1. Summary

`prompt-4d9e2f18-link-loss-detection.md` was implemented in full. Two commits,
`dd49e17` and `62af231`, two files.

The second commit matters and is described at §4.4: as first written, **the
change made link loss permanent**. The queue drain lived inside the gauge, and
the gauge is exactly what stops being drawn once the link is declared lost, so
nothing could ever be consumed and nothing could ever recover. It was caught by
driving recovery through the render loop instead of by calling `_note_sample`
directly, which is what the earlier assertions had done.

The connection indicator and the DISCONNECTED screen no longer ask whether a
Python thread is alive. They ask whether the adapter is delivering data, by
combining the transport's own view with a data-staleness timeout.

**The acceptance test discriminates.** With the world in the exact state of the
11:46 bench session — `obd_protocol` RUNNING, the socket still reporting
connected, no sample for ten seconds — the pre-change code draws **the gauge
with a green light** and the post-change code draws **the DISCONNECTED screen
with red**.

`pytest tests/` is **11 passed**, unchanged. 40 assertions pass post-change.

**Four departures from the prompt's sketch**, all recorded in §4. Three were
required for correctness: the prompt's literal EDIT 4 would have made OPTIONS
unreachable whenever the adapter was down; its edit list omitted a fourth call
site which, left alone, would have drawn the DISCONNECTED screen with dead
Setup and Simulate buttons; and its EDIT 2 placement of the drain made recovery
impossible.

**Not verified on target.** Everything below is bench evidence.

## 2. The Acceptance Test, Both Ways

The prompt required this written first and run against the unchanged file. It
was. It deliberately does **not** reference `_link_lost`, because the
pre-change file has no such method; it observes only what the operator saw —
which screen is drawn, and what colour the indicator resolves to — with the
world in the bench state:

* the `obd_protocol` thread is RUNNING (it always is; that is the defect)
* the transport reports **connected** (a powered-down adapter's socket does not
  fail until the next write)
* no sample has arrived for ten seconds

| | Pre-change (`HEAD`, in a worktree) | Post-change |
|---|---|---|
| Screen drawn by `_render_normal_modes` | **gauge** | **DISCONNECTED** |
| Colour resolved by `_draw_status_indicator` | **CONNECTED** (green) | **DISCONNECTED** (red) |
| Verdict | *"a stale needle and a green light"* | *"the operator is told the reading is dead"* |

That is the defect reproduced and then removed, by the same unchanged test
file.

**One correction made to the test during development**, recorded because it
changed what is being claimed. Its first version asserted the indicator was red
*within the rendered frame*. It is not drawn there at all:
`_render_normal_modes` returns immediately after `_render_disconnected()`, so
`_draw_status_indicator` never runs on that path. `_render_disconnected` draws
its own red border and red title instead. The assertion was corrected to
observe the indicator's own colour mapping directly, which is what the
requirement actually specifies. See §7.2 — this means the indicator's red
branch is nearly unreachable in practice.

## 3. What Was Changed

### 3.1 `manager.py` — constants and state

`LINK_LOSS_TIMEOUT = 2.0` and `LINK_RECOVERY_SAMPLES = 2` as class constants
beside `OPTIONS_PAGE_COUNT`. In `__init__`: `_last_sample_ts`,
`_link_connected_callback`, `_link_ok`, `_recovery_count`.

### 3.2 `manager.py` — `_drain_samples` and `_note_sample`

`_drain_samples` consumes the queue and is called from
`_render_normal_modes` **before** the link test, so arrivals are recorded
whatever screen is about to be drawn. It returns immediately in simulation
mode, so "a synthetic value is never evidence of an adapter" holds structurally
rather than by where the code happens to sit. `_draw_radial_mode` keeps only
the RPM conditioning. See §4.4 for why this placement is not optional.

`_note_sample` is called for every message drained, and **never** for a
synthetic value. Counts consecutive samples arriving within
the timeout of one another and latches `_link_ok` once
`LINK_RECOVERY_SAMPLES` have. Logs `Link restored` on the transition only.

### 3.3 `manager.py` — `_link_lost`

Two signals. `_sim_mode` is tested **first and unconditionally**. The callback
is read inside its own `try`; a raise or a `None` callback yields "socket state
unavailable", never "connected". Then: explicit `not connected` → lost; no
sample ever → lost; age past the timeout → lost, logging on the transition
only; otherwise `not self._link_ok`.

**Every failure path returns `True`.** The outer handler logs at ERROR and
returns `True`. There is no path in the method that returns `False` on failure,
asserted statically in §5.

### 3.4 `manager.py` — the four call sites

| Site | Was | Now |
|---|---|---|
| `_render_normal_modes` | `get_thread_status(...) != RUNNING and not _sim_mode` | `_link_lost() and mode == RADIAL` |
| `_draw_status_indicator` | `RUNNING → CONNECTED` | `_link_lost() → red`, `not _link_ok → yellow`, else green |
| `_current_view_key` | same thread-status expression | `_link_lost()` |
| `_register_view_regions` | same thread-status expression | `_link_lost() and mode == RADIAL` |

The `ThreadStatus` import was removed. `get_thread_status` now has **zero**
uses in the file and `ThreadStatus` survives only inside one explanatory
comment — checked, not assumed, as EDIT 5 required. `ThreadManager` is still
used as a type hint and remains imported.

### 3.5 `app.py` — injection at both sites

The guarded lambda is assigned at both `_start_setup_mode` (~line 206) and
`_start_normal_mode` (~line 316). `getattr(self, '_transport', None)` yields
`False` when there is no transport, which is correct during setup and before
`select_transport` has run. Nothing else in `app.py` changed.

## 4. Departures From the Prompt

### 4.1 The DISCONNECTED screen is gated on `mode == RADIAL` — REQUIRED

The prompt's EDIT 4 gives, literally:

```python
if self._link_lost():
    self._render_disconnected()
    return
```

`_render_normal_modes` dispatches RADIAL, OPTIONS **and** ACKNOWLEDGEMENT below
that return. So written literally, a lost link replaces the OPTIONS screen too.

That directly contradicts two things the prompt itself states:

> **constraint** — "Do NOT gate the OPTIONS or ACKNOWLEDGEMENT screens on link
> state. Settings must remain reachable with the adapter down."

> **test** — "OPTIONS and ACKNOWLEDGEMENT with the link lost. *Expected:* Still
> drawn; not replaced by the DISCONNECTED screen."

The condition is therefore `self._link_lost() and self.config.mode ==
DisplayMode.RADIAL`. The DISCONNECTED screen replaces the **gauge** — the thing
a lost link falsifies — not the settings screens.

This was latent rather than new: the pre-change condition had no mode gate
either, but it could never fire, so it never needed one. This change makes it
fire routinely. Without the gate, an operator whose adapter died could not
reach Simulate or Clear settings from OPTIONS at all — precisely when they are
most wanted.

### 4.2 `_register_view_regions` was missing from the edit list — REQUIRED

The prompt names three call sites. There is a fourth, at `manager.py:1413`,
carrying the identical thread-status expression, with a comment reading *"The
dispatch must mirror that order exactly."*

Left on thread status while `_current_view_key` moved to `_link_lost()`, the
sequence on a link loss would have been:

1. the key changes → re-registration is triggered;
2. `_register_view_regions` asks thread status → RUNNING → **not** disconnected
   → registers the gauge's regions, which are none;
3. `_render_normal_modes` asks `_link_lost()` → draws the DISCONNECTED screen.

**Setup and Simulate would be visible and dead**, on the operator's only route
out of a lost link. Fixing it is inside the permitted files, and is required by
the success criterion that `get_thread_status('obd_protocol')` not decide "the
disconnected screen" and by the issue's verification step *"The DISCONNECTED
screen's Setup and Simulate controls work when reached by this route."*

A dedicated assertion, `registration_matches_render_decision`, now checks for
all three modes that whatever `_render_normal_modes` draws is what
`_register_view_regions` registers.

### 4.3 `_note_sample` drops the latch on an observed gap — ROBUSTNESS

The prompt's EDIT 2 sketch resets `_recovery_count` when a gap exceeds the
timeout but leaves `_link_ok` set, then refreshes `_last_sample_ts`.

The flapping test exposed it. A link delivering one sample every 3 s with a 2 s
timeout reported **up** continuously: `_note_sample` refreshed the timestamp
before `_link_lost` was next consulted, so the staleness test never saw the
gap, and `return not self._link_ok` returned `False`.

In the live render loop this is masked — `_link_lost()` runs at 30 Hz and
clears the latch during the gap. But the prompt asks for the flapping outcome
to be *"assert[ed] explicitly rather than left to emerge"*, and the spec
describes `_link_ok` as *"cleared on any loss condition"*. A gap longer than
the timeout, observed inside `_note_sample`, is such a condition. Clearing it
there makes the guarantee structural instead of dependent on render cadence.

### 4.4 The drain was moved above the link gate — REQUIRED, and the near-miss

The prompt's EDIT 2 puts the sample bookkeeping "in `_draw_radial_mode`'s
queue-drain branch", where the drain has always lived. Implemented there, and
committed there in `dd49e17`, it makes **link loss permanent**:

1. `_link_lost()` becomes true;
2. `_render_normal_modes` renders the DISCONNECTED screen and returns —
   `_draw_radial_mode` is never called;
3. the drain lives inside `_draw_radial_mode`, so no message is consumed;
4. `_note_sample` never runs, `_last_sample_ts` never refreshes;
5. `_link_lost()` stays true for the life of the process.

Driven through the render loop with the adapter healthy again and samples
arriving at 20 Hz:

```
30 frames rendered
30 messages left unconsumed in the queue
30 of 30 frames DISCONNECTED
link recovered: False
```

A two-second dropout would have stranded the instrument on the DISCONNECTED
screen until restart. That is a worse operational outcome than the defect this
change removes, even though it is a safer one.

**Why the earlier assertions missed it.** They called `_note_sample()` directly
to simulate resumed data, which is not how the application drives it. The
prompt's own test — *"Recovery: samples resume at 20 Hz after a loss →
Gauge returns after LINK_RECOVERY_SAMPLES"* — passes when driven that way and
fails when driven through frames. A test that constructs the recovery it is
meant to observe cannot see this class of fault.

The drain is now `_drain_samples`, called from `_render_normal_modes` before
the link test. Two assertions pin it: `RECOVERY_through_the_render_loop`, which
renders frames and requires the queue empty and the gauge back; and
`drain_runs_on_every_screen`, below.

**A second starvation fixed by the same move.** `_draw_radial_mode` is only
called for `DisplayMode.RADIAL`, so sitting on the OPTIONS screen also drained
nothing. A healthy link went stale after two seconds and the indicator turned
red on the settings screen — and, worse, returning to the gauge would then show
DISCONNECTED. `drain_runs_on_every_screen` asserts OPTIONS and ACKNOWLEDGEMENT
keep the link fed.

### 4.5 Two smaller, non-behavioural departures

The bookkeeping is a named method `_note_sample` rather than nine lines inlined
in a `while` loop — identical semantics, and it makes the recovery rule
directly testable. The constants are referenced as `self.LINK_LOSS_TIMEOUT`,
since they are class attributes.

## 5. Testing

### 5.1 Environment

No installed dependencies and no `venv/` on this machine; `pygame`, `serial`,
`yaml` and `psutil` are stubbed on `PYTHONPATH` in the scratchpad. The `pygame`
stub gained a `Color` class for this work — without it `_draw_status_indicator`
raised into its own handler and the indicator silently read as `None`, which
would have made the acceptance test's second assertion meaningless.

Clock advance is simulated by back-dating `_last_sample_ts`, not by sleeping,
so the suite is deterministic and fast. `TouchEventCoordinator` is the real one.

No file was added to the repository.

### 5.3 What the 37 assertions cover

**Truth table** — data flowing → up; callback False with fresh data → lost
(the socket beats the data); no sample ever → lost; startup with no transport →
lost, and the DISCONNECTED screen shown while connecting, asserted as correct
rather than worked around.

**Simulation** — `_link_lost` False with the callback reporting disconnected
*and* no samples ever, the one case where every other signal says lost;
`_sim_mode` proved to be tested first by tokenising the method and comparing
positions; the gauge still drawn.

**Degradation** — absent callback with data → up; absent callback stale →
lost; raising callback → no exception escapes, falls through to staleness, and
is never treated as connected; an internally forced exception → `True`; and a
static check that the `except` block contains `return True` and no
`return False`.

**Recovery and flapping** — one sample after a long gap does not recover; two
do; samples every 3 s with a 2 s timeout never recover and the state does not
alternate; steady 20 Hz confirms after exactly `LINK_RECOVERY_SAMPLES` and does
not flap over 40 samples.

**Call sites** — the view key differs across a link change; OPTIONS and
ACKNOWLEDGEMENT are still drawn with the link lost; OPTIONS regions are still
*registered*; the DISCONNECTED screen's regions are registered when it
pre-empts the gauge; and registration matches the render decision for all three
modes.

**The drain and recovery** — `_drain_samples` sets no timestamp in simulation
mode, and neither does a whole simulated frame through
`_render_normal_modes`; the real path timestamps and latches; recovery driven
through 30 rendered frames empties the queue and returns the gauge within
`LINK_RECOVERY_SAMPLES`; and OPTIONS and ACKNOWLEDGEMENT keep the link fed
rather than starving it.

**Static** — no `get_thread_status` anywhere in the file; `_link_lost` logs
only `info` and `error` and its transition log is latch-guarded; both
`_link_lost` and `_note_sample` use `time.monotonic` and not `time.time()`;
`src/gtach/comm/` unmodified; exactly two files changed; `app.py` injects at
two sites, both guarded, with the guard's behaviour exercised rather than only
grepped.

## 7. Findings and Observations

### 7.1 Simulation mode's indicator changes from green to yellow — FOR DECISION

Pre-change, simulation showed **CONNECTED** (green), because the thread was
RUNNING. Post-change it shows **CONNECTING** (yellow): `_link_lost()` returns
`False` immediately for `_sim_mode`, but `_link_ok` is never latched, because
`_note_sample` is deliberately not called for synthetic values.

This follows the prompt's EDIT 4 exactly and does **not** violate the
constraint, which forbids simulation *reporting a lost link* — yellow is not
red. It is arguably more honest: there is no adapter. But it is a visible
change in a legitimate operating state that no T-Doc calls out, and a
persistent yellow dot may read as a fault.

Implemented as specified and **pinned by a test** (`sim_mode_indicator_is_never_red`)
so the behaviour is recorded rather than incidental. If green is wanted in
simulation, the fix is one clause; this is the operator's call, not the
executor's.

### 7.2 The indicator's red branch is nearly unreachable

`_render_normal_modes` returns immediately after `_render_disconnected()`, and
`_render_disconnected` draws no indicator. So on the normal path
`_draw_status_indicator` only runs when `_link_lost()` was `False` moments
earlier. Its `DISCONNECTED` branch can fire only on a state change between the
two calls within one frame.

In practice the indicator's live contribution is now **yellow vs green** —
green only once two samples confirm flow, where it was previously green
whenever the process was running. The red signal is carried by the whole
DISCONNECTED screen, which is red-bordered and red-titled.

This satisfies the issue's verification step *"the indicator is red whenever
the DISCONNECTED screen is shown"* only vacuously — there is no indicator on
that screen. Not a defect, and `_render_disconnected` is listed as unmodified
by the prompt, so it was left alone. Worth a decision on whether the dot
belongs on that screen at all.

### 7.3 A connected transport with no data yet now reads yellow, not green

`connected_but_unconfirmed_is_not_green` pins this. It is the honest state
between "the socket is open" and "data is arriving", and it did not exist
before.

### 7.4 Link assessment is coupled to the render loop

`_drain_samples` now runs on every `_render_normal_modes` frame rather than
only on gauge frames, which is what makes recovery and OPTIONS-while-connected
work (§4.4). But the coupling itself remains: **if the render loop stops or
stalls, no sample is recorded and the link will read as lost.**

That is the safe direction to fail, and the render loop stalling is its own
visible fault. Recorded because the property is now load-bearing — anything
that renders a screen outside `_render_normal_modes` for more than
`LINK_LOSS_TIMEOUT` will show a spurious loss. `SPLASH` and setup mode both
bypass it today, which is harmless because neither shows the gauge or the
indicator, but a future full-screen view would need the drain too.

The durable fix would be to drain in `_display_loop` rather than in the render
dispatch. That is a larger change than this prompt permits and is not required
for the defect at hand.

### 7.5 Test-harness defects found and fixed

Three, all in the checks rather than the source. The `pygame` stub lacked
`Color`, so `_draw_status_indicator` raised into its own handler and the
acceptance test's colour assertion read `None` — a check that could not have
distinguished red from green. One static assertion searched `code_only()`
output for a `getattr(self, '_transport', None)` whose string literal that
helper blanks by design. And `only_two_files_modified` compared against `HEAD`,
so it reported nothing once the work was committed; it is now a subset check
over uncommitted, untracked and committed paths together.

Recorded because all three are checks that pass for the wrong reason, which is
the failure mode that let §4.4 through in the first place.

## 8. What Was Deliberately Not Done

- **`src/gtach/comm/` — untouched.** `is_connected()` already exists on the
  interface; it is reached through the injected callback.
- **The `obd_protocol` thread is neither stopped nor restarted** on transport
  loss. It must survive to reconnect, and the watchdog would restart what it
  stopped.
- **`_render_disconnected` — unmodified**, per the prompt. See §7.2.
- **`LINK_LOSS_TIMEOUT` is not configurable.** A constant, as specified.
- **No test file added to the repository.**

## 9. What Only the Panel Can Answer

1. **Is 2.0 s the right timeout on real hardware?** It is 40–100 missed samples
   at the stated rate. If the adapter's real cadence is slower or burstier than
   assumed, the gauge will blank on healthy links.
2. **Does `is_connected()` on RFCOMM actually report `False` on a clean
   disconnect, and how fast?** The staleness backstop covers it either way, but
   the fast path is only fast if the socket is honest.
3. **§7.1 — is yellow acceptable in simulation mode?**
4. **§7.2 — should the DISCONNECTED screen carry the indicator dot?**
5. **Does the gauge blank on any normal driving transient?** The accepted cost
   of falling back to the DISCONNECTED screen is that a momentary loss blanks
   the gauge; only the vehicle can say how often that happens.
6. **The flat-battery reproduction itself** — power down the adapter mid-session
   and confirm the screen changes and the indicator turns red, which is the
   issue's twelfth verification step and the reason this change exists.
