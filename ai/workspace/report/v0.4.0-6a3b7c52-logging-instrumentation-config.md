## 1. Summary

`prompt-6a3b7c52-logging-instrumentation-config.md` was implemented in full.
One commit, `3ddefc3`, two files, +59 / −9 lines. Two small independent faults,
neither interacting with the other.

**(a) `debug.log` had never truncated or rotated.** `main.py` passed `mode='w'`
to `RotatingFileHandler`, which discards it whenever `maxBytes > 0`. It now
caps at 10 MB, keeps ten backups, and rolls over once at startup when the file
has content.

**(b) `PerformanceMonitor` was built with a literal `target_fps=60`.** It is now
constructed after `_load_config` with the configured rate, so at 30 Hz the
frame target, the dropped-frame threshold, the FPS alert and the history window
are all right for the first time.

**The rotation test discriminates.** Against `HEAD` it appends to the existing
log and produces no `debug.log.1`; against this commit the previous session is
preserved in `debug.log.1` and `debug.log` starts fresh.

`pytest tests/` is **11 passed**, unchanged. 35 assertions pass post-change.

No departures from the prompt were required. Two corrections were made to my
own test assertions, both recorded at §7.

**Not verified on target.** Everything below is bench evidence.

## 2. The Discriminating Test, Both Ways

Written first and run against the unchanged file, as the prompt required. It
calls `setup_logging` with both module-level log paths redirected into a
temporary directory and looks only at what lands on disk.

| | Pre-change (`HEAD`, in a worktree) | Post-change |
|---|---|---|
| `debug.log.1` exists | **False** | **True** |
| `debug.log.1` holds the previous session | **False** | **True** |
| `debug.log` still holds the previous session | **True** | **False** |
| `handler.mode` | `'a'` | `'a'` |
| `handler.backupCount` | `0` | `10` |
| `_DEBUG_MAX_BYTES` | `104857600` | `10485760` |
| Verdict | *"appended to, not rotated"* | *"each run has its own log"* |

`handler.mode` is `'a'` in **both** columns. That is the finding, not a
residual defect: the pre-change code asked for `'w'` and CPython silently gave
it `'a'`.

### 2.1 The CPython behaviour, reproduced directly

Before changing anything, against the standard library rather than by reading
the docs:

```
requested mode=w, actual handler.mode = 'a'
file content after construction: 'PRE-EXISTING\n'
```

`RotatingFileHandler.__init__` overrides the mode whenever `maxBytes > 0`, so
that rotation is not defeated by truncation. The `mode='w'` in `main.py` was
dead, and the comment above it claiming truncation at boot had been wrong since
it was written.

## 3. What Was Changed

### 3.1 `main.py` — the constants

`_DEBUG_MAX_BYTES` from 100 MB to 10 MB, and `_DEBUG_BACKUPS = 10` added, with
the prompt's comment recording the sizing and that `bin/gtach.service`'s
`StartLimitBurst=3` bounds a restart loop so rotate-at-start cannot exhaust the
slots.

### 3.2 `main.py` — `setup_logging`

The size is read **before** the handler is constructed, because construction
opens the file. The handler is then built with **no `mode` argument**, and a
non-empty log is rolled over explicitly. A rollover failure prints a warning in
the style of the existing `OSError` path and leaves the handler usable.

Rotation rather than truncation is the point: GTach runs under systemd with
`Restart=always`, and truncating would erase the evidence of the crash that
caused the restart.

`setLevel`, `setFormatter`, `addHandler` and the enclosing `OSError` handler
are unchanged. `_start_handler` is untouched.

### 3.3 `main.py` — `import os`

Added at module scope. `os` was previously imported **only inside**
`find_configuration_file` (`main.py:86`), so `setup_logging` had no `os` in
scope for `getsize`. Not a latent bug in the old code — the local import is
still there and still works — but the new code needs it at module level.

### 3.4 `manager.py` — the monitor moves

Removed from `_initialize_components`; constructed immediately after
`_load_config()` in `__init__`, guarded, falling back to
`DisplayConfig.fps_limit` when `fps_limit` is absent or non-positive, so there
is one default and no `ZeroDivisionError` from `monitor.py:42`.

Confirmed first, as the move depends on it, that `_load_config` does not
reference `performance_monitor` — it does not, asserted by a test rather than
left to the reading.

### 3.5 What fault (b) actually cost

Both figures the monitor derives from `target_fps` were wrong at 30 Hz:

| | `target_fps=60` (was) | `target_fps=30` (now) |
|---|---|---|
| `frame_time_target` | 16.67 ms | 33.33 ms |
| dropped-frame threshold (`1.5x`, `monitor.py:210`) | 25 ms | **50 ms** |
| `max_frame_time_ms` alert (`1.2x`) | 20 ms | 40 ms |
| `min_fps` alert (`0.8x`) | 48 | 24 |
| `_frame_history` window | 600 frames | 300 frames |

A 40 ms frame was counted as dropped; at the configured 30 Hz it is a healthy
frame with 60% of the budget spare. Asserted directly by
`dropped_frame_counted_against_the_configured_rate`.

## 4. The Monitor's Failure Semantics

The prompt asked for this to be established and stated rather than assumed.

**What was found.** `_display_loop` uses `self.performance_monitor` unguarded
at three points (`record_frame_start`, `record_frame_end`,
`should_log_periodic`) and is gated only on `PYGAME_AVAILABLE`.
`DisplayManager.display_available` is assigned three times and **never read**,
so it gates nothing — verified across the whole tree, where the other
`display_available` attributes belong to different classes that do read their
own.

**What that means.** Before this change, a monitor construction failure was
caught by `_initialize_components`' own handler, left the attribute unset, and
the display loop then raised `AttributeError` on every frame into its own
per-frame handler. It was already a broken loop, just a quietly broken one.

**What was done.** The new `except` reproduces that exactly: it logs at ERROR
and leaves the attribute unset. No fallback was invented, because inventing one
would be a behaviour change the prompt explicitly forbade. Pinned by
`monitor_failure_semantics_preserved`, which asserts the attribute is still
absent after a forced failure.

**One incidental improvement.** A monitor failure no longer aborts
`_ack_state_manager`, which used to sit after the monitor in the same `try`
block. Strictly better, and worth naming because it is a real difference.

This is worth its own issue: an unguarded dependency in the render loop whose
failure produces an infinite stream of caught exceptions rather than a
diagnosis. Out of scope here.

## 7. Findings and Observations

### 7.1 The prompt's eleven-start expectation is off by one — the code is right

The prompt expects that after *"eleven consecutive `setup_logging` calls"* the
*"eleventh-oldest line is gone"*. It is not, and should not be.

Eleven starts perform **ten** rotations: the first start finds no log and does
not rotate. So sessions 0–10 occupy `debug.log` plus `.1`–`.10` exactly, the
cap binds precisely, and nothing has been discarded yet. The **twelfth** start
is the one that drops session 0.

My first version of the test asserted the prompt's figure and failed. The
arithmetic was mine to get wrong, not the code's. It is now two assertions —
eleven starts lose nothing and produce no `.11`; twelve starts discard exactly
the oldest — which pins the boundary from both sides and is a stronger check
than the original.

### 7.2 I misread which constant is the dropped-frame threshold

While quantifying fault (b) I first reported the threshold as 20 ms / 40 ms.
That is `thresholds['max_frame_time_ms']`, the 120% alert. The dropped-frame
*counter* at `monitor.py:210` uses `frame_time_target * 1.5`, which is 25 ms
and 50 ms — exactly the figures the prompt gives. The prompt was right and my
first reading was not. Both thresholds were wrong at 30 Hz; the table at §3.5
now lists both, distinctly labelled.

### 7.3 `debug.log` is suppressed unless `--debug` is passed

The handler's level is `CRITICAL + 1` unless `--debug`. So in ordinary
operation `debug.log` receives nothing, stays empty, and — by the empty-file
rule — is never rotated and consumes no slot. Rotation pressure exists only
across debugging sessions. This makes the ten-slot budget considerably more
generous in practice than the sizing comment implies, which is the safe
direction.

### 7.4 The first restart on target will rotate the existing 43 MB file

Into `debug.log.1`. Expected, and named in the prompt. Worth pulling before it
ages out through ten further starts.

### 7.5 The startup line will report 30 FPS, not 60

Not a regression — the monitor telling the truth for the first time. Any
comparison against dropped-frame counts recorded in earlier sessions is
invalid, because those were measured against the wrong target.

### 7.6 One test-harness defect

`from gtach import main` yields the entry-point function rather than the
module, so the first version of the suite failed with `'function' object has no
attribute 'setup_logging'`. Recorded because it is a trap for the next person
writing a test against `main.py`.

## 8. What Was Deliberately Not Done

- **`monitor.py` — untouched.** It already accepts `target_fps`; the defect was
  the caller's argument.
- **No `set_target_fps` added.** `target_fps` is consumed three times during
  `__init__`; a setter would have to rebuild the history deque and recompute
  both alert thresholds.
- **`_load_config` and `_initialize_components` were not reordered.** Only the
  monitor's two lines moved.
- **`start.log`'s handler — unchanged.** Plain `FileHandler` honours `mode='w'`.
- **`debug.log` is not truncated at start.** It is rotated, for the
  `Restart=always` reason above.
- **No claim that this fixes the sluggishness of `ai/task.md` §9.12.** It
  reduces SD write volume. It does not establish that log I/O was the cause,
  and this report should not be cited as though it did.
- **The unguarded `performance_monitor` in `_display_loop`** (§4) was not
  guarded, because doing so would change behaviour the prompt required
  preserved.

## 9. What Only the Target Can Answer

1. **Is 10 MB about ninety minutes at 30 Hz?** The sizing comment asserts it;
   only a real debugging session on the Pi measures it.
2. **Does the rotation of the existing 43 MB file at first restart complete
   promptly** on the SD card, or delay startup noticeably?
3. **Do ten backups plus a live log fit the card's free space** alongside
   everything else, in the worst case of 110 MB.
4. **What the dropped-frame count actually is at 30 Hz**, now that it is
   measured against 50 ms rather than 25. This is the number §9.12 will need,
   and it has never been read correctly.
5. **Whether `StartLimitBurst=3` really does bound a restart loop** before the
   ten slots are consumed, under a genuine crash loop rather than in theory.
